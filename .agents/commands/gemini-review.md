# AI Command: Audit & Plan Gemini PR Review (`/gemini-review`)

This command provides a strict protocol to process code review comments generated by Gemini on GitHub Pull Requests. It analyzes each comment against the real codebase, filters out hallucinations and false positives, justifies every recommendation, and generates a structured implementation plan waiting for user confirmation before applying any change.

## 1. Context & Objective

During Pull Requests, Gemini automatically performs an initial code review. However, because Gemini primarily inspects git diffs in isolation, it may:
- Lack global architecture or cross-file context.
- Hallucinate non-existent APIs, methods, or package versions.
- Propose patterns contrary to Ascension project guidelines (e.g. suggesting Flutter Material `Icons.*` instead of `FLucideIcons`, removing doc metadata headers, etc.).
- Propose speculative or trivial comments that degrade code clarity.

**Goal:** Provide an impartial, high-seniority engineering assessment of each comment, determine what must be implemented, adapted, or rejected, and prepare a verified implementation plan for the user to review.

---

## 2. Input Format

The user may invoke this command with:
- A raw paste of Gemini's GitHub PR review (including `<details>`, markdown quotes `> ...`, or bullet lists).
- Individual comment excerpts with file paths and line numbers (`path/to/file:line`).
- A PR number or URL (if GitHub CLI / Git tools are accessible).

If no comments are provided in the initial prompt, politely prompt the user:
> *"Veuillez coller la liste des commentaires générés par Gemini sur votre PR afin que je puisse les analyser."*

## 3. Step-by-Step Execution Protocol

### Step 1: Parse & Locate

Extract each distinct suggestion:
- Target file path.
- Line number(s) or surrounding code block.
- Gemini's proposed observation and code replacement.

### Step 2: Inspect Real Codebase Context

For every identified file and line:
1. Open and view the actual file in the workspace using file reading tools.
2. Inspect the surrounding context (callers, imported packages, type definitions, architecture layer).
3. Check project conventions and rules:
   - **Mobile (`apps/mobile`)**: Flutter/Dart, Forui components, strict `FLucideIcons`, `flutter_animate`, `Skeletonizer`.
   - **Server (`apps/server`)**: Go idiomatic patterns, clean architecture, error wrapping, Gin handlers.
   - **AI (`apps/ai`)**: Python 3.11, MediaPipe/PyTorch pipelines, Pika, typed annotations.
   - **Documentation / Headers**: Retain all metadata headers (`@file`, `@brief`, `@project`, etc.). Never remove them.

### Step 3: Individual Comment Evaluation

Classify each comment under one of three verdicts:
- **`✅ Retenu (Valide)`**: The problem is genuine (real bug, memory leak, security issue, performance gain, clean architecture adherence) and Gemini's advice is relevant.
- **`⚠️ À adapter (Partiellement valide)`**: The issue raised is valid, but Gemini's suggested fix is incomplete, slightly hallucinated, or needs adjustments to match project conventions.
- **`❌ Rejeté (Invalide / Hallucination / Hors contexte)`**: The comment is based on a false premise, hallucinated APIs, lack of context, unnecessary bikeshedding, or contradicts Ascension standards.

For each comment, document:
- **Fichier & Ligne** : `path/to/file:line`
- **Suggestion de Gemini** : Résumé concis de la suggestion.
- **Verdict** : `✅ Retenu` / `⚠️ À adapter` / `❌ Rejeté`
- **Pourquoi (Justification technique)** : Analyse rigoureuse basée sur le code réel. Pourquoi c'est pertinent ou pourquoi c'est une hallucination / faux positif.
- **Ce que ça va changer (Impact)** : Effet concret sur le comportement, la robustesse, les performances ou la maintenabilité.

### Step 4: Generate Implementation Plan

Group all accepted (`✅`) and adapted (`⚠️`) suggestions into a clean, actionable Implementation Plan:
1. **Summary Table**:
   | Total Commentaires | ✅ Retenus | ⚠️ À adapter | ❌ Rejetés |
   |---|---|---|---|
2. **File-by-File Changes**:
   For each file to be modified:
   - Exact file path.
   - Concrete changes to apply with precise code snippets or diffs.
3. **Validation & Verification Commands**:
   List the commands to verify changes after execution (e.g., `dart analyze`, `flutter test`, `go test ./...`, `pytest`, `moon run ...`).

### Step 5: MANDATORY STOP — Wait for User Validation

> [!CRITICAL]
> **DO NOT EDIT ANY CODE FILES AT THIS STAGE.**
> Present the evaluation and the implementation plan, then explicitly ask the user for confirmation:
>
> *"Veuillez vérifier cette analyse et valider le plan d'implémentation (ou m'indiquer les ajustements souhaités sur certaines suggestions) avant que j'applique les modifications au code."*

### Step 6: Execution (Post-Approval Only)
Once the user validates the plan:
1. Apply the changes cleanly and minimally to the codebase.
2. Run appropriate linter/test commands to confirm no regressions.
3. Provide a final summary of modified files and verification results.

- Use clear markdown typography and code fences.
- Maintain professional, objective, senior-level tone.
